**Why it happened:** `claim()` ran a SELECT for the next claimable task, then a separate UPDATE to mark it running. The SELECT wasn't inside a transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran without holding a lock. Two workers could both read the same pending row before either UPDATE took the write lock, then both marked it running and returned it. The original commit, 1aa1954, acknowledged this: "Two workers claiming at the same instant can get the same task; optimize later if it becomes a problem."

**How it was fixed (commit 3b07992):** `claim()` now runs `BEGIN IMMEDIATE` before the SELECT. That takes the write lock first, so a second worker waits until the first commits and then sees the task as running. The fix has since moved into `taskq/repository.py`, where `claim()` still issues `BEGIN IMMEDIATE` before its SELECT. The commit also added a regression test, `test_concurrent_claims_never_return_the_same_task`. It uses two threads and an `_after_select_hook` that sleeps between the SELECT and UPDATE to make the race reliable. The commit says the test fails without `BEGIN IMMEDIATE` and passes with it.

**Rejected alternative:** The commit and history don't record one. The only rejected option I found is in the earlier design: the simple SELECT-then-UPDATE was chosen deliberately, with the race accepted for later. A common alternative I didn't find discussed is a single atomic UPDATE that selects and claims in one statement, for example with `RETURNING` or by checking the row count. I can't confirm from the repo that it was considered and rejected.
