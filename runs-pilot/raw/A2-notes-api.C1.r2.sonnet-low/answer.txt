**Root cause:** `PATCH /notes/:id` passed the raw request body straight to `store.patch()`. That function did `Object.assign(note, changes)`, and nothing filtered or validated the body first. Any key a client sent was written onto the stored record, including `id` and `createdAt`. Because `createdAt` is stored as epoch ms, sending `createdAt: 0` turned the creation date into 1970-01-01. POST and PUT weren't affected, because `validateNoteInput` copies out only `title` and `body`.

**Fix** (commit `e9d532a`):
- **New `validateNotePatch`** in `src/validation.ts`. It accepts only `title` and `body`, and applies the same rules as create (non-empty title, length limits, string types). It returns 422 for any other field, an empty patch, or an invalid value. The authors chose strict rejection over silently ignoring unknown fields, so a client that sends `id` or `createdAt` finds out instead of assuming it took effect.
- **`src/server.ts`** now runs the body through `validateNotePatch` and passes only the validated result to the store.
- **`src/store.ts`** no longer uses `Object.assign`. It copies `title` and `body` explicitly, so the store itself can't overwrite `id` or `createdAt`.
- **Tests** cover two cases. Sending `id` or `createdAt` returns 422 and leaves the note unchanged. Invalid `title` or `body` values, and an empty `{}`, also return 422.
