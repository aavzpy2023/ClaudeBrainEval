**How it was fixed.** Commit `3b07992` ("Fix duplicate task hand-out when workers claim concurrently") changed `claim()` so its SELECT and UPDATE run inside one `BEGIN IMMEDIATE` transaction. The write lock is now taken before the SELECT, so a second worker waits until the first commits and then sees the row as `running`. The current version is `Repository.claim` in `taskq/repository.py:120`, after the SQL was moved into the `Repository` class. It keeps the `BEGIN IMMEDIATE` line and the same SELECT/UPDATE shape, and it now also checks `not_before` for retry backoff.

**Why it happened.** The original `claim()` ran its SELECT and UPDATE as separate statements, with no transaction around the SELECT. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran without a lock. Two workers could both read the same pending row before either UPDATE took the write lock. Both then marked it `running` and returned it.

**Regression test.** The same commit added `test_concurrent_claims_never_return_the_same_task`. It runs two threads against two tasks and uses an `_after_select_hook` that sleeps between the SELECT and the UPDATE, which makes the race deterministic. The commit message says the test fails without `BEGIN IMMEDIATE` and passes with it. I did not re-run the test here.
