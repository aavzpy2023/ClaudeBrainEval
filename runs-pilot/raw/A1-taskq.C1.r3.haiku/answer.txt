**How it was fixed:** commit `3b07992` ("Fix duplicate task hand-out when workers claim concurrently") wraps `claim()` in a `BEGIN IMMEDIATE` transaction. The write lock is taken before the SELECT, so a second worker waits until the first commits and then sees the task as `running`. The commit also adds `test_concurrent_claims_never_return_the_same_task` in `tests/test_storage.py`. It uses two threads and a `_after_select_hook` that sleeps between the SELECT and the UPDATE, which makes the race happen every time. The test fails without the change and passes with it.

**Why it happened:** `claim()` ran its SELECT and its UPDATE as separate statements. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran with no lock held. Two workers could both read the same pending row before either UPDATE took the write lock, and both would mark it running and return it. The bug was known from the start: commit `1aa1954` ("Add claim and done workers with a 60 s task lease") says so explicitly, and chose the simple version to be optimized later.

The only rejected alternative in the history is for a different decision: "higher = more urgent" for priorities, in `adbc93b`. If you remember a discussion of another option, such as a single conditional UPDATE, that isn't in the repo, so I can't confirm it from here.
