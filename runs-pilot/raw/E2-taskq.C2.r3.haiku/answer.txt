taskq upgrades old database files in place, every time it opens one. There is no version number or migration history. `Repository._connect()` in `taskq/repository.py:54-74` does this on each connection:

1. `CREATE TABLE IF NOT EXISTS tasks (id, payload)` creates the table if the file is empty or missing.
2. It reads the column list with `PRAGMA table_info(tasks)`.
3. For each newer column that's missing, it runs `ALTER TABLE tasks ADD COLUMN ...`. The columns are `status` (default `'pending'`), `lease_expires`, `priority` (default 5), `attempts` (default 0) and `not_before`.

Because each step checks before it adds, the process is idempotent: a current-format file passes through unchanged. Existing rows get the defaults, so an old task comes back as pending, priority 5, zero attempts. `test_migrates_old_schema` in `tests/test_repository.py:92-102` covers this: it builds a bare `(id, payload)` table, claims the row, and checks that it shows up as priority 5.

Things to be aware of:

- **Only the columns are checked.** Nothing checks the data itself, so a future change that alters an existing column's meaning would need its own step. The `SCHEMA_VERSION = 1` in `taskq/cli.py:11` only versions the JSON output, not the database.
- **Downgrades aren't handled.** An older taskq opening a newer file would miss the extra columns and fail on the first query that uses them.
- **Old files outside the default location aren't found.** The default is now `~/.taskq/queue.db`, so a database left at the old working-directory path is ignored unless you point `TASKQ_DB` at it. This comes from the project digest, which I did not check against `default_db_path()`.
