**How it was fixed:** In commit 3b07992, `claim()` now runs `BEGIN IMMEDIATE` before its SELECT, so the write lock is taken first. A second worker waits until the first commits, then sees the task as `running` and skips it. The commit also adds a regression test that uses two threads and a `_after_select_hook` sleep to widen the race window. The test fails without the fix and passes with it. The code now lives in `taskq/repository.py` (lines 125–134) after the 3f22710 refactor.

**Why it happened:** Commit 1aa1954 added `claim` as two separate statements: a SELECT for the next claimable task, then an UPDATE to mark it running. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran with no lock held. Two workers could both read the same pending row before either UPDATE took the write lock, and both would return it. That commit's message says so directly: "Two workers claiming at the same instant can get the same task; optimize later if it becomes a problem."

**Rejected alternative:** The repository doesn't record one. Neither 3b07992 nor its neighbours say which fix was considered and turned down. The closest thing is the deferral in 1aa1954, which chose the simple version and postponed the fix. Other options that would have closed the race, such as a single atomic `UPDATE ... RETURNING` or a conditional UPDATE that checks rowcount, aren't mentioned anywhere in the history. If you want the actual reasoning, the ClaudeBrain session logs for this project may hold it.
