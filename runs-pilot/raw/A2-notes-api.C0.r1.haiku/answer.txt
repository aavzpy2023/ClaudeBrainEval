**Root cause:** `PATCH /notes/:id` passed the raw parsed request body straight to `store.patch()`, which did `Object.assign(note, changes)`. Nothing filtered or validated the keys, so any field a client sent was written onto the stored record, including `id` and `createdAt`. Because `createdAt` is stored as epoch ms, a client sending `createdAt: 0` would set the note's creation date to 1970-01-01. POST and PUT were safe only because `validateNoteInput` copies out just `title` and `body`.

The bug was introduced in `2da92fb` ("Add PATCH /notes/:id for partial updates"), which added the `Object.assign` call.

**Fix:** Commit `e9d532a` ("Fix PATCH overwriting id and createdAt; reject unknown fields with 422"):

- **`src/validation.ts`:** added `validateNotePatch`. It accepts only `title` and `body`, applies the same rules as create, and returns 422 for any other field, an empty patch, or an invalid value. The commit chose strict rejection over silently dropping unknown fields so client bugs surface instead of being hidden.
- **`src/server.ts`:** the PATCH handler now runs the body through `validateNotePatch` and passes only the validated `value` to the store.
- **`src/store.ts`:** `patch()` copies `title` and `body` explicitly instead of using `Object.assign`, so it can't write other fields even if called with a bad object.
- **`test/notes.test.ts`:** added tests for title-only and body-only patches, plus 404 and 400 cases. The commit diff doesn't show a test for the id/createdAt rejection itself, so that path is covered only by the code change.
