**Why it happened.** `claim()` ran a SELECT and then an UPDATE, and the SELECT wasn't inside a transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT, UPDATE, DELETE). The SELECT therefore ran with no lock held. Two workers could both SELECT the same pending row before either UPDATE took the write lock. Both then marked it running and returned it.

**The fix** is commit `3b07992`. `claim()` in `taskq/storage.py` now runs `BEGIN IMMEDIATE` before the SELECT, so the write lock is taken first. A second worker waits until the first commits, then sees the task as running.

The commit also adds a regression test. Two threads call `claim()` on a two-task queue. A test-only hook, `_after_select_hook`, sleeps between the SELECT and the UPDATE to make the race deterministic. The test fails without `BEGIN IMMEDIATE` and passes with it.
