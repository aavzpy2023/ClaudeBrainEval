**Root cause:** `PATCH /notes/:id` passed the raw request body straight to `store.patch()`, which did `Object.assign(note, changes)`. Nothing filtered or validated the body, so any key a client sent was written onto the stored record, including `id` and `createdAt`. Since `createdAt` is stored as epoch ms, a client sending `createdAt: 0` would make the note show `1970-01-01`. POST and PUT were safe only because `validateNoteInput` copies out just `title` and `body`.

**Fix (commit `e9d532a`):**
- **`src/validation.ts`:** added `validateNotePatch`. It accepts only `title` and `body`, with the same rules as create. It returns 422 for any other field, an empty patch, or an invalid value. Strict rejection was chosen over silently dropping unknown fields, because silent drops hide client bugs.
- **`src/store.ts`:** `patch` now copies only `title` and `body` (`if (changes.title !== undefined) note.title = changes.title;` and the same for `body`), instead of `Object.assign`. Even if validation were bypassed, `id` and `createdAt` can no longer be overwritten.
- **`test/notes.test.ts`:** added tests for the new behavior.

I checked the current source and the commit diff, and both match this. The store's `patch` signature is still typed as `Partial<NoteInput>`, so the copy-only-two-fields logic is the real protection at that layer, not the type.
