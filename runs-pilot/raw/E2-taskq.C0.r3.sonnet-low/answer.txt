taskq upgrades old databases automatically, in `Repository._connect()` (`taskq/repository.py:54-74`). It runs every time a connection is opened. There is no version number or separate migration step.

1. It runs `CREATE TABLE IF NOT EXISTS tasks`. This creates only the original two columns, `id` and `payload`. An existing table is left alone.
2. It reads the table's current columns with `PRAGMA table_info(tasks)`.
3. For each newer column that is missing, it runs `ALTER TABLE tasks ADD COLUMN`:
   - `status TEXT NOT NULL DEFAULT 'pending'`
   - `lease_expires REAL` (nullable)
   - `priority INTEGER NOT NULL DEFAULT <DEFAULT_PRIORITY>`
   - `attempts INTEGER NOT NULL DEFAULT 0`
   - `not_before REAL` (nullable)

Rows from an old database get sensible values. They become `pending`, at default priority, with 0 attempts and no lease or delay.

The check runs on every connection and adds only the columns that are missing. A database that is already current is unaffected, and a database from any older version is brought up to date.

The test `test_migrates_old_schema` in `tests/test_repository.py:92` covers this. It builds a table with only `id` and `payload` and checks that it is upgraded.

I didn't check whether two processes opening an old database at the same moment could both try the `ALTER TABLE`. The second one would fail with a "duplicate column" error. I also didn't check whether anything guards against that.
