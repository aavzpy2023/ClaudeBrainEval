taskq upgrades old databases in place, in `Repository._connect()` (`taskq/repository.py:54-74`). Every operation opens its connection through that method, so the check runs each time.

1. It runs `CREATE TABLE IF NOT EXISTS tasks`, which creates only `id` and `payload`. An existing table is left alone.
2. It reads the table's current columns with `PRAGMA table_info(tasks)`.
3. For each newer column that is missing, it runs `ALTER TABLE tasks ADD COLUMN`:
   - `status TEXT NOT NULL DEFAULT 'pending'`
   - `lease_expires REAL`, which is nullable
   - `priority INTEGER NOT NULL DEFAULT 5`, the default priority
   - `attempts INTEGER NOT NULL DEFAULT 0`
   - `not_before REAL`, which is nullable

Rows from an old file therefore read as pending tasks with default priority, zero attempts, no lease and no backoff delay.

- **No version number:** there's no `user_version` or migrations table. The upgrade is column-presence checks only. That works for adding columns. It wouldn't handle renaming or retyping a column, or backfilling data.
- **Concurrency:** I didn't see any locking around the `ALTER`s. If two processes open an old file at the same moment, one could try to add a column the other just added and raise an `OperationalError`. I haven't tested this.
- **Older `./taskq.db` files:** this covers old schemas at the current path. Files at the old cwd-relative `./taskq.db` path aren't moved automatically. As the project notes say, set `TASKQ_DB` to point at them.
