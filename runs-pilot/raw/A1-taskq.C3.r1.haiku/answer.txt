**Why it happened:** `claim()` ran a SELECT for the next pending task, then an UPDATE to mark it running, with nothing holding a lock between them. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran outside any transaction. Two workers could both SELECT the same pending row before either UPDATE took the write lock. Both then marked it running and returned it. The root cause and the fix are in commit `3b07992`.

**How it was fixed:** `claim()` now runs `BEGIN IMMEDIATE` before the SELECT (`taskq/repository.py`, around line 134). That takes the write lock first, so a second worker waits until the first commits and then sees the task as `running`. The commit also added a regression test that uses two threads and an `_after_select_hook` that sleeps between the SELECT and UPDATE. The test fails without `BEGIN IMMEDIATE` and passes with it. The code now carries a comment explaining why the explicit `BEGIN` is needed.
