**The fix:** `Repository.claim` now runs `BEGIN IMMEDIATE` before its SELECT. That takes SQLite's write lock up front, so the select-then-mark-running sequence is atomic. This was commit `3b07992`.

**Why it happened:** Python's `sqlite3` module doesn't open a transaction before a SELECT. It only opens one implicitly before a DML statement such as UPDATE. Two workers could therefore both run the SELECT and see the same `queued` task. Each would then UPDATE it to `running`, and both would be handed the task. The read and the write were not one atomic step.

**What was rejected:** a lock file, to serialize claimers outside the database. You chose not to use one. `BEGIN IMMEDIATE` gets the same mutual exclusion from SQLite itself, with no extra file to manage.
