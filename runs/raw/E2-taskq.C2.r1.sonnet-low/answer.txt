taskq upgrades old databases automatically, in place, each time it opens a connection. The code is in `Repository._connect` (`taskq/repository.py:54-74`).

1. It runs `CREATE TABLE IF NOT EXISTS tasks`, which defines only `id` and `payload`. An old file that already has the table is left alone.
2. It reads the existing columns with `PRAGMA table_info(tasks)`.
3. For each newer column that is missing, it runs `ALTER TABLE ... ADD COLUMN`. The defaults are:
   - `status` is `'pending'`.
   - `lease_expires` is `NULL`.
   - `priority` is `DEFAULT_PRIORITY`, which is 5.
   - `attempts` is `0`.
   - `not_before` is `NULL`.

Old rows therefore become ordinary pending tasks at default priority, with no retries used and no backoff delay.

- **No schema version:** It checks which columns exist rather than using a version number or `user_version`. A future change that isn't an added column, such as a rename or a type change, would need different handling.
- **Concurrent first open:** I didn't see any locking around the migration. If two processes open an old database at the same moment, one `ALTER` could fail with "duplicate column name". I haven't tested this.
- **Old `./taskq.db` files:** Nothing moves them to the new default path, `~/.taskq/queue.db`. You have to point `TASKQ_DB` at them. After that, they get the column upgrade described above.
