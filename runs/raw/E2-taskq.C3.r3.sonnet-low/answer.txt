taskq upgrades old database files in place, with a lightweight migration that runs every time `Repository._connect()` opens the database (`taskq/repository.py:54-74`).

1. It runs `CREATE TABLE IF NOT EXISTS tasks`, which defines only `id` and `payload`. An old file that already has the table is left alone.
2. It reads the existing columns with `PRAGMA table_info(tasks)`.
3. For each newer column that is missing, it runs `ALTER TABLE tasks ADD COLUMN`:
   - `status TEXT NOT NULL DEFAULT 'pending'`
   - `lease_expires REAL`
   - `priority INTEGER NOT NULL DEFAULT 5`, the default priority
   - `attempts INTEGER NOT NULL DEFAULT 0`
   - `not_before REAL`, which is nullable

Existing rows are backfilled by those defaults. Old tasks become `pending`, priority 5, with 0 attempts and no backoff delay. The checks are idempotent, so already-migrated files pass through unchanged.

- **No schema version:** It doesn't use `user_version` or a migrations table. Each column is checked by name, so a new column needs one more `if` block.
- **Only adds columns:** It can't rename, drop, or retype a column.
- **Runs on every connection:** Each `_connect()` pays for a `PRAGMA` call. There is no lock around the migration, so two processes could race on an old file. I haven't checked how the code handles that.
- **Old `./taskq.db` files:** Since the default moved to `~/.taskq/queue.db`, files in the working directory aren't picked up automatically. Point `TASKQ_DB` at one to migrate it.
