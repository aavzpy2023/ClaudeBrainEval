**Short answer:** The fix is `BEGIN IMMEDIATE` before the SELECT in `claim()`. The alternative the project rejected was a lock file.

**Why it happened:** `claim()` ran its SELECT and UPDATE as separate steps, and the SELECT wasn't inside a transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran with no lock held. Two workers could both SELECT the same pending row before either UPDATE took the write lock. Both then marked it `running` and returned it. The commit message for `3b07992` records this root cause.

**How it was fixed:** `claim()` now runs `conn.execute("BEGIN IMMEDIATE")` before the SELECT (`taskq/repository.py:134`). The write lock is taken first, so a second worker waits until the first commits and then sees the task as `running`. The SELECT and UPDATE happen in one transaction. A regression test uses two threads and the `_after_select_hook` test hook to widen the race window. It fails without `BEGIN IMMEDIATE` and passes with it.

**Rejected alternative:** A lock file. The project notes in `CLAUDE.md` say "No lock file, by the user's choice." The notes record the decision but not the user's reasons.
