The root cause was that `PATCH /notes/:id` passed the raw request body straight into the store, which merged it onto the stored record with `Object.assign`. Nothing filtered the keys, so a client could send `id` or `createdAt` and overwrite them. Because `createdAt` is stored as epoch milliseconds, sending `createdAt: 0` made the note read as 1970-01-01. POST and PUT were safe only because `validateNoteInput` copies out just `title` and `body`.

The fix is in commit `e9d532a` ("Fix PATCH overwriting id and createdAt; reject unknown fields with 422"):

- **`src/validation.ts`**: a new `validateNotePatch` accepts only `title` and `body`, applying the same rules as create. It returns a 422 for any other field, an empty patch, a non-object body, or an invalid value. The commit chose strict rejection over silently dropping unknown fields, so client bugs surface instead of being hidden.
- **`src/store.ts`**: `patch()` no longer uses `Object.assign`. It copies only `title` and `body` onto the note, so even a bypass of validation couldn't touch `id` or `createdAt`.
- **`src/server.ts`**: the PATCH handler calls `validateNotePatch` and passes its sanitized `result.value` to the store.
- **`test/notes.test.ts`**: 18 lines of tests were added for this behavior.
