taskq upgrades old database files in place, with a lightweight migration that runs every time it opens a connection. The code is in `Repository._connect()` in `taskq/repository.py:54-74`.

1. **Base table:** it runs `CREATE TABLE IF NOT EXISTS tasks (id, payload)`. This is the original v1 schema, so a brand-new database starts from there too.
2. **Column check:** it reads the existing columns with `PRAGMA table_info(tasks)`.
3. **Adding missing columns:** each newer column that isn't there gets an `ALTER TABLE tasks ADD COLUMN ...`. Every added column has a default, so existing rows stay valid:
   - `status TEXT NOT NULL DEFAULT 'pending'`
   - `lease_expires REAL`, which is nullable.
   - `priority INTEGER NOT NULL DEFAULT DEFAULT_PRIORITY`
   - `attempts INTEGER NOT NULL DEFAULT 0`
   - `not_before REAL`, which is nullable.

Old tasks therefore appear as pending, default-priority tasks with no retries and no backoff delay.

- **No schema version:** there is no version number or `user_version`. Each column is checked on its own, so a database from any older version gets exactly the columns it lacks.
- **Extra work on every connection:** the check repeats on each `_connect()`. It's cheap, but it is extra work every time.
- **Concurrency:** I didn't check whether two processes migrating at the same moment could collide on an `ALTER`.
- **Test:** `tests/test_repository.py:92` has `test_migrates_old_schema`, which builds a v1-style table and checks it gets migrated. I didn't run it.
