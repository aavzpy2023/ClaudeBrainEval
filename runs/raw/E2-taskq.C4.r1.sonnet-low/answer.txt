taskq migrates old databases automatically, in `Repository._connect()` (`taskq/repository.py:54-74`). It runs every time a connection is opened:

1. It runs `CREATE TABLE IF NOT EXISTS tasks`, with only `id` and `payload`. This is the original schema, so a brand-new database gets built up from it.
2. It reads the existing columns with `PRAGMA table_info(tasks)`.
3. For each column that is missing, it runs `ALTER TABLE tasks ADD COLUMN ...`. These are the columns it checks:
   - `status`, `TEXT NOT NULL DEFAULT 'pending'`
   - `lease_expires`, `REAL`, nullable
   - `priority`, `INTEGER NOT NULL DEFAULT 5`
   - `attempts`, `INTEGER NOT NULL DEFAULT 0`
   - `not_before`, `REAL`, nullable

Old rows get sensible values. They become `pending` at the default priority 5, with 0 attempts and no lease or backoff.

- **No version number.** It doesn't use `PRAGMA user_version` or a migrations table. It checks which columns exist, so any older version's database is upgraded in one pass.
- **Additive only.** It never renames, drops or retypes a column.
- **Runs on every connection.** The check is a cheap PRAGMA, but it is repeated each time. I didn't look at whether two processes migrating at the same moment could collide on the `ALTER`.

This only covers old schemas. As the project notes say, old cwd-relative `./taskq.db` files aren't moved to the new `~/.taskq/queue.db` default. You have to point `TASKQ_DB` at them.
