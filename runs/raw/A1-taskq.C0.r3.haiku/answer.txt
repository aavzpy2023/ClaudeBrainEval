**Why it happened:** `claim()` ran its SELECT and its UPDATE as separate statements, and the SELECT wasn't inside a transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT ran with no lock held. Two workers could both read the same pending row before either UPDATE took the write lock, and both would mark it running and return it. The original commit (`1aa1954`) knew about this: its message says "Two workers claiming at the same instant can get the same task; optimize later if it becomes a problem."

**How it was fixed (commit `3b07992`):** `claim()` now runs `BEGIN IMMEDIATE` before the SELECT. That takes the write lock first, so a second worker waits until the first commits and then sees the task as `running`. The code now lives in `taskq/repository.py`, since `storage.py` was later moved there. The current `claim()` at `taskq/repository.py:118-150` keeps the same `BEGIN IMMEDIATE` pattern. The commit also added `test_concurrent_claims_never_return_the_same_task`, which uses two threads and an `_after_select_hook` sleep to force the race. The test fails without the fix and passes with it.

**Rejected alternative:** The repo does not record one. Neither the fix commit nor the code comments mention an alternative that was considered and turned down. The only "rejected" notes in the history are about priority numbering (`adbc93b`) and jitter in retry backoff, which are unrelated.

If you want the reasoning captured, the choice would most likely have been between `BEGIN IMMEDIATE` and a single conditional UPDATE (`UPDATE ... WHERE id = ? AND status = 'pending'` with a rowcount check). That is my inference, not something the repo says, so I'd suggest adding a note to the code or commit if you know which one was weighed.
