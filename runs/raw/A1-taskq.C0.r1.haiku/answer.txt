**Why it happened:** `claim()` ran its SELECT and UPDATE as separate steps, and the SELECT ran outside any transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), so the SELECT held no lock. Two workers could both read the same pending row before either UPDATE took the write lock. Both then marked it `running` and returned it.

**How it was fixed (commit 3b07992):** `claim()` now runs `BEGIN IMMEDIATE` before the SELECT. That takes the write lock first, so a second worker waits until the first commits, then sees the task as `running` and skips it. The commit also added a regression test: two threads, plus a `_after_select_hook` that sleeps between the SELECT and UPDATE to make the race reliable. The test fails without `BEGIN IMMEDIATE` and passes with it.

The code has since moved. `claim()` now lives in `taskq/repository.py` (commit 3f22710), and the same `BEGIN IMMEDIATE` is still there.
