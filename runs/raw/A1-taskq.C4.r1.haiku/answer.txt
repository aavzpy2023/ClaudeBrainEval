**Fix:** `claim()` now opens a `BEGIN IMMEDIATE` transaction before its `SELECT`, so the write lock is taken first. A second worker that calls `claim()` at the same time waits until the first commits, then sees the task as `running` and skips it. The fix is commit `3b07992`, and it added a regression test with two threads and an `_after_select_hook` that widens the race window. The code now lives in `taskq/repository.py` (lines 120–147), because the SQL was later moved there in `3f22710`. The commit touched `taskq/storage.py`, which no longer exists.

**Why it happened:** `claim()` ran its `SELECT` and `UPDATE` as separate steps, and the `SELECT` ran outside any transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT/UPDATE/DELETE), not before a SELECT. So two workers could both read the same pending row before either `UPDATE` took the write lock. Both then marked it `running` and returned it.
