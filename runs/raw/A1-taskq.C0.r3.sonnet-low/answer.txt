**Why it happened** (commit `3b07992`): `claim()` did a SELECT and then an UPDATE, and the SELECT ran outside any transaction. Python's `sqlite3` only opens an implicit transaction before DML (INSERT, UPDATE, DELETE). So the SELECT held no lock. Two workers could both SELECT the same pending row before either one's UPDATE took the write lock. Both then marked it running and returned it.

**How it was fixed:** `claim()` now runs `BEGIN IMMEDIATE` before the SELECT. That takes the write lock first, so a second worker waits until the first commits and then sees the task as running. The commit also added a regression test. It uses two threads and a test hook, `_after_select_hook`, which sleeps between the SELECT and the UPDATE to make the race deterministic. The test fails without `BEGIN IMMEDIATE` and passes with it. The SQL has since moved into `Repository` in `taskq/repository.py`, where the docstring still describes the single-transaction approach.
